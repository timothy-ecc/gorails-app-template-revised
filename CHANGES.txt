CHANGES.txt - GoRails App Template upgrade to Rails 8.1
========================================================
Verified against: Rails 8.1.4, Ruby 4.0.6, Propshaft 1.3, Solid Queue/Cache/Cable, Devise 5.0.4
Full test suite passes (`rake`): generates a throwaway app, asserts creation, `yarn build`, and
that the generated app boots.


1. Background jobs: Sidekiq -> Solid Queue
-----------------------------------------
* Dropped `sidekiq` gem, `config.active_job.queue_adapter = :sidekiq`, the `/sidekiq` mount and
  the `Sidekiq::Web` require from `template.rb`.
* `Procfile` and `Procfile.dev` worker is now `bin/jobs` (the executable `solid_queue:install`
  generates, which `rails new` already runs).
* Dropped `config/cable.yml` from the payload. `solid_cable:install` writes the correct file
  (async/test/solid_cable -> `connects_to: database: writing: cable`) and the gem's template is
  versioned with the gem, so there is nothing for us to maintain.
* Dropped `whenever`. It is a cron wrapper, not a long-running process, so there is no `clock:`
  Procfile entry to add. Add `clockwork`/`cronic` later if you actually need an in-process scheduler.

2. Removed code that could not work
-----------------------------------
* Impersonation: deleted `app/controllers/madmin/impersonates_controller.rb`, the `/madmin/impersonates`
  routes, the navbar banner, and `impersonates :user` from `ApplicationController` and
  `ApplicationCable::Connection`. No current gem defines `impersonates`/`true_user`/`icon`, so the app
  raised on boot (`ApplicationController`) and 500'd on every page render (the banner's `icon()` call).
* Twitter: removed `omniauth-twitter`, the `twitter` omniauth callback, the provider entry in the
  generated Devise initializer, and `Service#twitter_client` plus the `client`/`expired?`/`access_token`
  scaffolding that only existed to serve it (it also used `Rails.application.secrets`, removed in Rails 8).
  `Service` keeps `belongs_to :user` and the per-provider scopes.
* `default_to_esbuild` (set `options[:javascript]` after `rails new` had already run the JS step) and
  `read_gemfile?` (dead fallback) are gone; the guard is now `rails_8_or_newer?`.
* `devise:install`'s `config.secret_key` line: no longer patched, Devise 5 defaults to
  `application.secret_key_base`. The development `default_url_options` line was removed too, since
  Rails 8.1's `development.rb` already sets it.
* FriendlyId migration is no longer rewritten with `[5.2]`. FriendlyId 5.7 already emits
  `ActiveRecord::Migration["#{MAJOR}.#{MINOR}"]`; the insert produced
  `ActiveRecord::Migration[5.2]["8.1"]`, which blows up at migrate time.
* `github/workflows/verify.yml` deleted. `rails new` now generates a complete `.github/workflows/ci.yml`.

3. Propshaft
------------
* Deleted `app/assets/config/manifest.js` (Sprockets-only; Rails 8 no longer generates it).
* `add_users` no longer targets the newest migration by mtime; it globs
  `db/migrate/*_create_users.rb` (solid_* generate migrations in the same directory, so mtime was racy).
* `app/assets/stylesheets/application.css` is still removed, so Propshaft serves only the built CSS.

4. Turbo, not rails-ujs
----------------------
* Dropped `@rails/ujs`, `@rails/request.js` and the unused `trix` from `add_javascript`, and
  `require("@rails/ujs").start()` from `app/javascript/application.js`.
* OmniAuth links in `app/views/devise/shared/_links.html.erb` are now
  `button_to ..., method: :post, data: { turbo: false }` (Devise 5's own pattern).
* Deactivate link in `registrations/edit.html.erb` uses `data: { turbo_method: :delete, turbo_confirm: ... }`.
* Scaffold `_form` Destroy link: same treatment (`turbo_method`/`turbo_confirm`).

5. Asset build
--------------
* `add_javascript` now installs the `esbuild` npm package. The template bundles its own
  `esbuild.config.mjs`, which does `import * as esbuild from "esbuild"`; without the package
  `yarn build` died with `ERR_MODULE_NOT_FOUND` (pre-existing, and the reason the integration test
  could not go green).
* `add_esbuild_script` collapsed to `npm pkg set scripts.build=...` + `yarn build`; the `npx -v`
  version probe existed only to choose between deprecated `npm set-script` and `npm pkg set`.

6. Look and feel
----------------
* `lib/templates/erb/scaffold/show.html.erb` converted from Bootstrap 4 (`page-header`,
  `btn btn-default`, `dl-horizontal`) to Bootstrap 5, matching our `index.html.erb`.
* Navbar: impersonation banner removed, `far fa-bell` -> `bi bi-bell`.
* `app/views/shared/_head.html.erb`: dropped the Font Awesome 6.0.0-beta2 CDN link (2021 beta, long dead).
  Bootstrap Icons ship with `css:install:bootstrap`.
* `ApplicationController` regained Rails 8.1's `allow_browser versions: :modern` and
  `stale_when_importmap_changes`, which the payload had been dropping.

7. Fixture fix (pre-existing, unrelated to Rails 8)
--------------------------------------------------
* Devise's generated `test/fixtures/users.yml` is `one: {}` / `two: {}`, and the users table has
  `email null: false, default: ""` plus a unique index, so loading fixtures raised
  `UNIQUE constraint failed: users.email`. Any DB-touching test in a generated app errored.
* The template now ships `test/fixtures/users.yml` with two users that have distinct emails and
  `Devise::Encryptor.digest` passwords, so `fixtures :all` works and the `services` fixture's
  `user: one` / `user: two` references resolve. `copy_templates` gained `directory "test"`.

8. Copying config
-----------------
* `copy_templates` no longer runs `directory "config", force: true`. With no `config` payload,
  Thor resolved it against railties' own templates and overwrote the generated app's config --
  including putting Redis back into `config/cable.yml` right after `solid_cable:install` had
  replaced it. Removing the line is the fix; re-running the installer afterwards would only paper
  over it.

11. Solid Queue in development
------------------------------
Found by a generated app: `bin/dev` died with `Could not find table 'solid_queue_processes'`.
* Cause: Rails 8.1's `rails new` only defines a separate `queue:` database for *production* (and
  `solid_queue:install` only patches `production.rb`). In development `SolidQueue.connects_to` is
  nil, so `SolidQueue::Record` uses the primary database -- whose schema comes from `db/schema.rb`.
  `db/queue_schema.rb` is only loaded for a config with `migrations_paths: db/queue_migrate`, so
  nothing created the queue tables in development and `Procfile.dev`'s `worker: bin/jobs` died.
* New payload `lib/tasks/solid_queue.rake` loads `db/queue_schema.rb` into the primary database
  from `db:prepare` and `db:setup` (`db:reset` runs `db:drop` + `db:setup`). It skips when
  `config.solid_queue.connects_to` is set -- production, or a development `queue:` database added
  following Solid Queue's README, where `db:prepare` already loads the schema -- and when the
  tables already exist, since `db/queue_schema.rb` creates tables `force: :cascade`.
* `test/template_test.rb` now runs `bin/rails db:prepare` in the generated app and asserts
  `SolidQueue::Process.table_exists?`, which is the check that would have caught this.
* `README.md` notes that `db:prepare` also creates the tables `bin/jobs` needs.
* `Procfile.dev` is unchanged: a self-heal there cannot work, because with no database at all
  (`bin/dev` without `db:prepare`) the check raises instead of creating anything.
* Second half of the same bug: development kept Rails' inline `ActiveJob::QueueAdapters::Async`
  adapter, so even with the tables present `perform_later` never reached Solid Queue and the
  worker polled an empty queue forever. `template.rb` now appends
  `config.active_job.queue_adapter = :solid_queue` to the generated
  `config/environments/development.rb` -- no `connects_to`, since development uses the primary
  database. `test/template_test.rb` asserts both the tables and the adapter.
* Verified end to end in a generated app: `perform_later` writes a `solid_queue_jobs` row and
  `bin/jobs` claims and finishes it.
* Footgun to know about: in development, jobs only run if the worker is running. Use `bin/dev`
  rather than `bin/rails server` alone, or jobs sit in the queue.

12. Selectable scheduler and CSS framework (added 2026-09-28)
-----------------------------------------------------------
* `template.rb` asks two questions after the base install, before `add_gems`: the job scheduler
  (`SCHEDULER`: solid_queue/sidekiq/none) and the CSS framework (`CSS`:
  bootstrap/tailwind/simple/none). Both default to what the template used to hardcode, so a
  non-interactive run is unchanged.
* Asked *before* `add_gems`, not in `after_bundle`: `Thor::Actions::Gem#invoke!` runs
  `bundle install` again for a gem added late, so asking first keeps it to one bundle.
* Selection is `ENV[key] || ask(...) || default`. Not Thor's `ask ... limit_to:`: on closed stdin
  (CI, a scripted `rails new`) `ask` returns *nil* rather than the default, and `ask_filtered`
  loops forever on nil. Anything unrecognised falls back to the default.
* Production's job adapter was being set by accident: `solid_queue:install` gsub-rewrites
  `production.rb`'s commented-out `queue_adapter = :resque` line into `:solid_queue`. Thor's
  `environment` action injects at the *top* of the `configure do` block, so an injected line would
  lose to that one. `set_queue_adapter` gsubs `production.rb` directly.
* `Procfile`/`Procfile.dev` are still a single payload; the `worker:` line is gsubbed afterwards
  (`bin/jobs` / `bundle exec sidekiq` / removed) rather than shipping three copies of each file.
* `copy_templates` no longer copies `lib` wholesale. `lib/tasks` (Solid Queue only) and
  `lib/templates` (a CSS framework only) are copied separately, so a sidekiq app gets no
  `solid_queue.rake` and an unstyled app gets no Bootstrap scaffold templates.
* `app/` is the Bootstrap payload and `variants/{tailwind,simple,none}` are overlays copied over it,
  so the default install pays nothing. Consequence: an overlay file that is missing is not an error,
  it silently leaves Bootstrap classes behind, and `bootstrap_helper.rb` / `jumpstart/` have to be
  removed explicitly. The test asserts the overlay landed.
* Thor's `directory` defaults its *destination* to the source path (`directory "doc"` writes to
  `doc/`), so the overlay copy needs an explicit destination: `directory "variants/tailwind", "."`.
* The account menu is a Bootstrap dropdown, i.e. it needs Bootstrap's JavaScript. The non-Bootstrap
  overlays use a `<details>` element instead, so logout and notifications are reachable with no
  JavaScript.
* `AnnouncementsHelper` is framework-specific too (`text-success` etc.), so tailwind ships its own
  copy. Tailwind v4's automatic source detection does pick up classes out of `.rb` files, which is
  how the unread-announcement dot and the announcement colors reach the stylesheet.
* The four CSS answers split into two groups, and `css_build?` is the whole of that split: bootstrap
  and tailwind are installed by `css:install:*`, so they need the gem, a build step, a `css:`
  foreman process and matching scaffold templates. simple and none are plain files Propshaft serves
  as they are, and get Rails' own `application.css` and Rails' own scaffold templates.
* `CSS=simple` (simple.css v2) is vendored at `variants/simple/app/assets/stylesheets/simple.css`:
  9.7KB minified, MIT, no `url()` or `@import`, local font stacks, so a generated app needs no
  network and no build step. To update it, curl `https://cdn.simplecss.org/simple.min.css` over that
  file and put the version header back. It is deliberately not a CDN `<link>` or an npm package:
  this template ships everything locally, and a `rails new` that depends on a CDN or on a build step
  for a 10KB file is a worse trade than a file that can go stale.
* simple.css is classless, so it styles the same plain HTML as the `none` overlay: `copy_templates`
  copies `variants/none` and then `variants/simple` over it, and the second overlay only has to
  carry what actually differs — the stylesheet and a layout that links it. The link sits *before*
  `render 'shared/head'` in the layout because that partial links `application.css`, and the app's
  own rules have to win.
* No simple.css scaffold templates: `rails g scaffold` already emits semantic HTML, which is all a
  classless stylesheet needs. Five more templates to keep in sync was not worth it.
* The announcement rules for `simple` and `none` are appended to `application.css`, including the
  three `text-success`/`text-warning`/`text-danger` type colors. The plain views emit those classes
  and only Bootstrap ever styled them, so before this they were dead in both variants. The warning
  color is `#b45309`, not Bootstrap's `#ffc107`, which is unreadable on white.
* Gotcha: Tailwind v4 scans from the enclosing git root, so an app generated *inside* another
  repository has that repository scanned too. Harmless in a generated app, but it means the
  `.text-green-600` assertion in `test/template_test.rb` can pass locally by finding the class in
  this repo's own `variants/`; CI removes `.git` first, so there it can only come from the
  generated app.

Not changed, on purpose
-----------------------
* importmap-rails and `config/importmap.rb`: madmin depends on importmap-rails, and the Stimulus app
  that our `controllers/index.js` imports is generated by its installer. Dropping the direct Gemfile
  line would be cosmetic and would cost another bundle run.
* Rails 8.1's multi-database `production` configuration (solid_queue/solid_cache/solid_cable each
  get their own database) and `madmin:install` remaining a documented post-install step.
